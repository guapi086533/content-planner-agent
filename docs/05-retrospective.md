# 复盘与下一步

## 最难的问题

最容易出错的是重规划后的费用和状态。预算不能只取新档位的报价：已经生成过的其他脚本仍然发生过费用。也不能因为模型说保存成功就标完成，必须确认相应档位脚本成功、报价仍可行，并且状态与保存结果在同一事务提交。

实现将“历史发生过什么”保留在事件记录，将“当前能使用什么”放在素材、脚本和账本中。失败后的重试可以更新当前步骤状态，但不能抹掉旧失败。这让失败续跑、部分成功和重复执行可以共享同一套状态，而不是补几段条件分支。

另一个实际困难是模型额度。早期测试 qwen-plus 等型号失败后，没有覆盖用户账户中实际有额度的所有型号；用户根据控制台截图指出 `qwen3.8-27b` 可用，随后真实调用和 14 组场景验证成功。这说明应区分某型号额度不足与整个账户不可用，先查看实际可用模型再建议充值。早期失败记录已保留，也没有修改账户计费设置。

真实运行还暴露了离线规则未暴露的问题：一条停止说明把模拟分误标为 SIM。补充提示及 `*_units` 字段后，针对性复验正确给出 3 SIM 预算及 9/5/1 SIM 缺口。程序账本前后保持正确；原始错误说明与修正后输出均保留，不能仅用费用断言通过掩盖模型文字错误。

## 本轮实现收获

本轮工程实践说明了三个边界：模型负责选择动作，工具负责报告真实结果，程序负责不可绕过的预算/依赖/持久化约束。三者混在一起会让固定工作流伪装成 Agent，也会让自然语言状态覆盖真实执行状态。

幂等应有明确范围：本项目是同一数据库中的同一业务请求 ID，不是所有环境中的全局去重。SQLite 能让本地状态和保存方案原子提交，但不能自动保证未来真实发布接口的 exactly-once。后续接入外部工具时，需要把业务幂等键传给服务，并保存外部回执。

本文件是 AI 对本轮实现过程的复盘，不代替候选人自己的学习陈述。候选人未提供独立学习与修改记录，提交前应补充实际经历。

## 优先改进顺序

1. 在现有真实路径基础上增加不同主题与预算边界，复查模型的单位、缺口和状态说明是否与工具事实一致。
2. 对相同场景多次运行，比较成功率、费用超限拦截、无效调用和总决策次数，再决定是否修改提示或工具描述，保留修改前后证据。
3. 增加主题和素材覆盖、内容质量检查，把模板脚本替换为可审校的真实生成服务；保留来源引用与人工审核状态。
4. 接入真实费用和工具时，加入预授权、外部幂等键、超时状态查询及补偿策略，区分“请求超时”与“对方实际未执行”。
5. 如需长时间运行，再考虑历史压缩、状态版本迁移、租约调度、可视化和部署；这些不属于本轮核心验收。
