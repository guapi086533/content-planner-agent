# AI 辅助说明与个人贡献

## 协作方式

本项目使用 Codex 辅助开发。我主要参与选题、需求输入、交付范围确认及模型接入过程中的调整；Codex 承担方案细化、代码实现、自动测试、示例生成和文档整理。以下分别记录个人参与、AI 使用范围和已有验证结果。

## 我的参与与判断

### 选题与需求输入

我选择了“内容任务规划 Agent”，向 AI 提供完整题干和统一提交规范，要求围绕预算、截止时间、工具失败、重复执行等验收点完成项目。需求来源于考核题目，具体流程拆解及工程设计由 Codex 辅助完成。

### 交付范围确认

我确认先完成本地项目与 Git 提交，再进行 GitHub 交付。这一安排使本轮工作先形成可运行代码、验证材料和可审阅版本。

### 模型选择与接入调整

最初调用 `qwen-plus` 返回免费额度不足。收到错误后，我进入百炼控制台查看实际可用额度，发现 `qwen3.8-27b` 仍有额度，并提出直接改用该型号，而不是继续坚持原来的模型配置。

Codex 随后执行了接口与原生工具调用测试，确认新型号可用，并将它设为项目默认模型，补齐真实模型运行记录。这个调整是我在协作中提出的具体建议，也使项目从离线流程验证推进到真实模型决策验证。

这次排查说明，某个型号额度不足不等于整枚 API Key 或整个账户都不可用，选择模型时需要结合实际额度与工具调用能力判断。

本机已有 50 项自动测试、14 组离线案例及 14 组真实模型场景的状态/费用检查记录。金额单位说明修正后，另对正常完成、预算降级、预算无解进行了 3 组针对性复验。

上述命令由 Codex 在本机执行，实际输出、模型响应 ID 和 Trace 已保存。本人参与了模型可用性排查与切换建议；目前尚未补充本人独立运行这些命令或手工修改工程代码的记录。

## 模型与工具的三层区别

1. **开发辅助模型**：本次 Codex 对话中的 AI，用于编写项目，不等于项目运行时模型。
2. **项目运行时模型**：`--mode live` 通过外部接口请求 `qwen3.8-27b` 选择工具；真实动作、观察、响应 ID 和 usage 已记录。早期 qwen-plus 因免费额度不足失败，另存于 provider-errors，未用后续成功记录覆盖。
3. **离线测试策略**：`--mode offline` 的 `OfflineModel` 是固定 Python 规则，不调用大模型。工具均为允许的本地合成业务函数。离线 Trace 和 HTTP 单元测试替身都不是运行时模型智能的证据。

没有提交模型内部思维过程。Trace 中的 reason 仅是动作依据的简短公开说明；HTTP 适配器主动丢弃 `reasoning_content`。检查环境时只显示变量名和脱敏错误码，密钥值未写入仓库。`.env`、SQLite 运行状态及本地 runs 目录被 Git 忽略。
